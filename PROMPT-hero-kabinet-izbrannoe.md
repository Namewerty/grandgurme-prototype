# Первый экран с роликом бренда, личный кабинет и избранное

Задание для Claude Code в папке «Сайт» (репозиторий
https://github.com/Namewerty/grandgurme-prototype, ветка `main`). Две части,
каждая в своей ветке и со своей проверкой: сначала первый экран, потом кабинет.

Работа идёт в прототипе и в общих исходниках. На стенд 1С-Битрикс
`https://bitrix.grandgurme.ru` изменения перенесёт Cowork после твоей сдачи,
поэтому PHP-шаблоны, страницы стенда и скрипты для командной PHP-строки
в этой задаче ты не пишешь. От тебя нужно, чтобы прототип был готов к переносу:
одна граница данных, обычные формы, все тексты в файлах данных и записка
о переносе (раздел Б.13).

Решения в задании приняты Денисом. Если код подсказывает, что какое-то из них
неудобно реализовать, реализуй как написано и запиши расхождение в таблицу
«Решения, принятые иначе» — у каждой части она своя, в её разделе README.
Вопросов по ходу не задавай. Единственное исключение — из `CLAUDE.md`: если патч
из `_patches/` не применяется, остановись и покажи это Денису.

- Цифр, сроков, адресов, часов работы и способов связи не придумывать. Там, где
  значение нужно, а данных нет, ставь пометку `⚠ ПОДТВЕРДИТЬ У ЗАКАЗЧИКА` в файле
  рядом со значением и добавь строку в таблицу «Что осталось предварительным».
- Скругления только `--radius-pill`, `--radius-card`, `--radius-card-sm`, 0.
  Теней и золотых заливок нет. В стилях только токены из `tokens.css`, сырых
  цветов нет; исключение — `rgba(10,13,17,…)` в затемнении первого экрана,
  как сейчас. Бирюзовый — только интерактив и активные состояния, как записано
  в README.
- Контраст текста не ниже 4.5:1, как записано в README «Доступность».
- Тексты интерфейса живут в `src/data/*-copy.js`, тексты первого экрана —
  в `src/data/hero.js`. В разметке строк нет. Тексты в задании финальные.
  Везде, где стоит «{n} позиции» или «{n} товаров», число склоняется через
  `plural()` из `src/js/catalog/model.js`.
- Не трогать обмен с 1С, выгрузку и типы цен. PHP и собранные файлы
  в `bitrix/templates/**` и `deploy-src/**` руками не править: `npm run bitrix`
  обновляет собранное сам. README шаблона править можно.

### А.2. Что в ролике и почему это решает композицию

Ролик — нарезка производства и бренда:

- 0–1,5 с — тёмное макро;
- 1,5–13,9 с — разделка, посол и копчение рыбы, много светлых планов; самые
  яркие — белая доска на 2,4–4,3 с и 8,6–9,6 с;
- 13,9–17,6 с — упаковка №1 Caviar и Siberian Luxury Bar на синем фоне;
- 17,8–20,3 с — всплеск воды на тёмном фоне и золотой логотип
  «№1 ГРАНД ГУРМЭ» в центре кадра.

Ролик идёт по кругу. В горизонтальном файле логотип занимает по горизонтали
31–69 %, по вертикали 38–60 % («№1» — 38–47 %, надпись — 53–60 %).

**Зона логотипа** — прямоугольник логотипа с запасом 3 % с каждой стороны,
в долях видимого кадра:

| Что на экране | По горизонтали | По вертикали |
|---|---|---|
| горизонтальный файл, кадр 16:9 без обрезки | 28–72 % | 35–63 % |
| горизонтальный файл в квадратном кадре (`cover`) | 13–87 % | 35–63 % |
| вертикальный файл 4:5 | 5–95 % | 35–63 % |
| широкая раскладка (`cover` по размеру секции) | считать по размеру `<video>` из 28–72 % × 35–63 % исходника | |

Два требования к первому экрану. Текст и кнопки не заходят в зону логотипа
ни на одном проверяемом размере экрана. Светлые планы не съедают текст.

### А.4. Широкая раскладка

Работает при `(orientation: landscape) and (min-width: 768px) and (min-height: 600px)`.

Видео во весь первый экран, высота секции 88svh, как сейчас. Центр кадра
свободен, весь текст собран в полосу у нижнего края:

```
┌───────────────────────────────────────────────────────────────┐
│ [шапка поверх видео]                                          │
│                                                               │
│                                                               │
│                      ( зона логотипа )                        │
│                                                               │
│                                                               │
│ МЕЖДУНАРОДНЫЙ ГАСТРОБУТИК · С 1982 ГОДА                       │
│ Деликатесы, которые подают                                    │
│ в 300 ресторанах мира          [Смотреть икру] [Весь каталог] │
└───────────────────────────────────────────────────────────────┘
```

- Разметка: `.hero__content` занимает всю ширину (`grid-column: 1 / -1`)
  и сам становится сеткой из 12 колонок. Внутри — `.hero__heading`
  (надзаголовок и H1) в колонках 1–8 и `.hero__actions`. От 1280px кнопки
  стоят в колонках 9–12, прижаты вправо и к нижней линии H1 (`align-self: end`).
  Уже 1280px кнопки стоят под заголовком слева. `createExit` по-прежнему
  двигает и гасит `.hero__content`, поэтому `display: contents` здесь нельзя.
- H1 — `clamp(2.2rem, 2.9vw, 2.75rem)`, каждая из двух строк держится в одну
  строку. Нижний отступ секции — `clamp(2.5rem, 7vh, 4.5rem)`.
- Запас под параллакс меньше: высота видео 124 % секции (`inset: -12% 0`)
  вместо 140 %, сдвиг при уходе 8 % вместо 12 %. Кадр меньше увеличен, края
  упаковки и логотипа не срезаются. Комментарий в CSS про запас обнови.
- Затемнение `.hero__scrim` — три слоя:
  1. сверху под шапку: `rgba(10,13,17,.55)` у верхнего края, прозрачный
     на 22 % высоты;
  2. снизу под текст: `rgba(10,13,17,.9)` у нижнего края, `.8` на 20 %
     высоты, `.55` на 27 %, прозрачный на 36 %;
  3. ровный слой `rgba(10,13,17,.12)` на весь кадр.

  На 1440×900 надзаголовок стоит примерно на 21–25 % высоты от низа, низ
  логотипа — на 38 %: плотная часть затемнения должна закончиться между ними.
  Значения стартовые, подбирай их только по проверке А.7.
- Надзаголовок сейчас золотой (`--gold-fg`, в тёмной секции это `--gold`).
  Золотой текст набирает 4.5:1 только на почти чёрном фоне. Если на светлых
  кадрах он не проходит проверку контраста при затемнении, которое ещё
  не гасит логотип, надзаголовок в hero переходит на цвет `--on-dark`,
  а золотой остаётся линия перед ним. В отчёте напиши, какой вариант остался.
- Если на каком-то из проверяемых размеров текст заходит в зону логотипа
  (скорее всего это 1366×768, 1280×720 и 1024×768), уменьши H1, зазоры и нижний
  отступ медиазапросом по `max-height`. Прятать текст или поднимать его
  к центру нельзя.
- Заметку README о том, что при 88svh снизу виден край `#trust`, оставь только
  для широкой раскладки.

### А.5. Узкая раскладка

Всё, что не широкое: экраны в портретной ориентации любой ширины и низкие
горизонтальные экраны (высота меньше 600px, телефон, повёрнутый набок).

Горизонтальный ролик во весь экран телефона обрезается до пятой части ширины,
и логотип в финале режется. Поэтому здесь видео стоит кадром сверху, текст —
под ним:

```
┌──────────────────────┐
│ [шапка поверх видео] │
│                      │
│      видео 4:5       │
│   ( зона логотипа )  │
│                      │
│▒▒▒ переход в void ▒▒▒│
│ МЕЖДУНАРОДНЫЙ …      │
│ Деликатесы, которые  │
│ подают в 300         │
│ ресторанах мира      │
│ [   Смотреть икру  ] │
│ [   Весь каталог   ] │
└──────────────────────┘
```

- `.hero__media` — блок во всю ширину под прозрачной шапкой; секция
  по-прежнему заходит под шапку отрицательным `margin-top`.
- Пропорция кадра:
  - 4:5 — портрет уже 768px, вертикальный файл;
  - 1:1 — портрет от 768px, горизонтальный файл;
  - 16:9 — низкий горизонтальный экран, горизонтальный файл.
- Выбор файла в `hero.js` делается один раз, как сейчас, но по условию
  `(max-width: 767px) and (orientation: portrait)`: повёрнутый телефон получает
  горизонтальный файл.
- Видео внутри кадра — `inset: 0; height: 100%; object-fit: cover`, без запаса
  под параллакс. Параллакс видео в узкой раскладке выключен; уход текста при
  прокрутке остаётся.
- Затемнение: сверху под шапку от `.55` до прозрачного на 30 % высоты кадра;
  нижние 22 % кадра переходят в `--void`.
- Текст стоит на `--void` под кадром и заходит на кадр на 2.5rem, чтобы кадр
  и текст читались одним экраном. В зону логотипа текст не заходит.
- Кнопки уже 480px — во всю ширину, одна под другой; шире — в ряд.
- Высота секции — по содержимому, правило 88svh здесь не действует.

### А.7. Проверка

Headless Chrome, кадры в `screenshots/hero-video/`.

Как останавливать ролик. `media.js` запускает видео через IntersectionObserver
и может снова вызвать `play()` после смены размера окна. В сценарии проверки
до загрузки страницы подмени `HTMLMediaElement.prototype.play` на функцию,
которая ничего не запускает и возвращает выполненный промис. Перед снимком
выставь `video.currentTime = t`, дождись `seeked` и проверь, что `video.paused`.
В код сайта ради проверки ничего не добавляй.

Размеры: 1920×1080, 1440×900, 1366×768, 1280×720, 1024×768, 1024×1366, 768×1024,
844×390, 390×844, 375×667. Секунды: 0,5 · 3,8 · 9,2 · 16,8 · 20,0.

- **Зона логотипа.** На кадре 20,0 с посчитай зону на экране по таблице А.2
  (для широкой раскладки — по размеру `<video>` и правилу `object-fit: cover`)
  и сравни с `getBoundingClientRect()` надзаголовка, обеих строк H1 и кнопок.
  Пересечений нет ни на одном размере.
- **Контраст.** На кадрах 3,8, 9,2 и 16,8 с сними фон с `visibility: hidden`
  у текста и кнопок. Возьми 95-й перцентиль яркости пикселей под прямоугольниками
  надзаголовка, H1 и кнопок. Надзаголовок и H1 — не меньше 4.5:1 к цвету текста;
  у кнопки с обводкой текст — 4.5:1, обводка — 3:1.
- **Логотип виден.** Над прямоугольником самого логотипа (без запаса)
  непрозрачность затемнения не больше `.2` на всех размерах. Слои складываются
  как `1 − (1 − a₁)(1 − a₂)(1 − a₃)`.
- Результаты трёх пунктов — одной таблицей в отчёте: размер, пересечение,
  контраст надзаголовка, H1 и кнопок, непрозрачность над логотипом.
- Шапка поверх видео читается на кадре 3,8 с (белая доска).
- `prefers-reduced-motion: reduce`: ролик не запускается, виден постер,
  интро нет.
- Запрет видео (`canLoadVideo()` возвращает false): постер, текст читается.
- `/alt` открывается и работает.
- Ни горизонтальной прокрутки, ни исключений в консоли.
- `npm run bitrix` проходит, в собранном `app.js` нет строки «ПРОЛИСТАЙТЕ».

## Часть Б. Личный кабинет, вход и избранное

Ветка `feature/account` от `main` после слияния части А.

### Б.1. Решения

1. **Вход только по номеру телефона и одноразовому коду.** Паролей нет, входа
   по почте нет, кнопок «Войти через Google» и «Войти через Apple» нет. Телефон
   уже главный контакт на оформлении, и по российским правилам авторизации
   номер телефона — разрешённый способ входа. VK ID, Яндекс ID и Сбер ID тоже
   разрешены; это второй темп, в этой задаче их нет.
2. **Вход и регистрация — один сценарий.** Человек вводит номер и код. Если
   номер новый, после кода появляется короткий шаг «Как к вам обращаться»,
   и кабинет создан.
3. **Оформление без входа остаётся.** На оформлении вход предлагается одной
   строкой и ничего не блокирует.
4. **Заказы и заявки, оформленные без входа, попадают в кабинет** того, чей
   номер указан в контактах, при каждом входе с этим номером.
5. **Избранное работает без входа** и хранится в браузере. При входе избранное
   гостя переходит в кабинет, а в браузере очищается. После выхода избранное
   в браузере пустое. У избранного свой адрес `/favorites`; прежний
   `/account?tab=favorites` уходит отовсюду.
6. **Корзина при входе складывается** с корзиной кабинета. Одинаковые позиции
   не удваиваются: остаётся большее из двух количеств. Гостевая корзина после
   этого очищается. При выходе корзина остаётся в кабинете, а в браузере
   становится пустой.
7. **Отменить или изменить заказ из кабинета нельзя.** На странице заказа для
   этого есть связь с менеджером.
8. **Сердец на витрине главной `#shop` нет** — решение из шапки `shop.js`
   остаётся в силе. Сердце есть в сетке раздела каталога, на карточке товара,
   в лентах карточки товара, на обзоре кабинета и на `/favorites`.
9. **В этой задаче не делаем:** вход через VK ID, Яндекс ID и Сбер ID, бонусы
   и программу лояльности, «Сообщить о поступлении», сохранённые карты,
   отдельный раздел получателей, отзывы.

  адресов. Внутри `account.js` страница выбирается по `location.pathname`.

#### Формы данных

Записаны JSDoc-типами в `api.js`.

```
User      { id, phone, name, lastName, email, marketing, createdAt }
Address   { id, label, street, apartment, intercom, isDefault, createdAt }

Order     запись заказа, как её сейчас кладёт submitCheckout
          ({ number, createdAt, contact, receive, shipments, payment, comment,
             promo, items, totals }), плюс:
          userId          кому принадлежит, null у гостевого до привязки
          status          статус заказа (см. словарь в Б.6)
          shipments[i].status   статус отгрузки

Request   запись заявки, как сейчас ({ number, createdAt, contact, items,

- `phone` в аргументах — десять цифр без +7 (`phoneDigits` из `validate.js`).
  В записях заказов телефон хранится отформатированным, как сейчас; сравнение
  — по цифрам.
- Статус заказа с двумя отгрузками — статус той отгрузки, которая дальше

#### `api.js`

Все функции асинхронные. `resendIn` и `retryIn` — в секундах.

```
requestCode(phone)            → { ok: true, resendIn, codeLength }
                              | { ok: false, error: 'rate_limit', retryIn }
verifyCode(phone, code)       → { ok: true, isNew, user }
                              | { ok: false, error: 'wrong_code', attemptsLeft }
                              | { ok: false, error: 'attempts_exhausted' | 'expired' }
completeProfile({ name, email, marketing })
                              → { ok: true, user } | { ok: false, errors }
getUser()                     → User | null
logout()
getHistory({ type, page })    → { items: [HistoryRow], total }   type: 'all' | 'orders' | 'requests'
getOrder(number)              → Order | null      только свой
getRequest(number)            → Request | null    только своя
reorder(number)               → { added, skipped: [name] }
getAddresses()                → [Address]
saveAddress(address)          → { ok: true, address } | { ok: false, errors }
                                | { ok: false, error: 'limit' | 'duplicate' }
deleteAddress(id)
setDefaultAddress(id)
saveProfile({ name, lastName, email, marketing })
                              → { ok: true, user } | { ok: false, errors }
requestPhoneChange(phone)     → как requestCode | { ok: false, error: 'phone_taken' }
confirmPhoneChange(code)      → { ok: true, user } | ошибки как у verifyCode
deleteAccount()               → { ok: true }
getFavorites()                → [снимок позиции]
addFavorite(snapshot)
removeFavorite(id)
```

**Как `api.js` ведёт себя в прототипе:**

- СМС не отправляется. Подходит код `123456` для любого номера.
- Константы в начале файла, у каждой пометка
  `⚠ ПОДТВЕРДИТЬ: на Битриксе значение задаёт ядро`: `CODE_LENGTH = 6`,
  `RESEND_SECONDS = 60`, `MAX_ATTEMPTS = 3`, `CODE_TTL_MINUTES = 10`,
  `MAX_CODES_PER_HOUR = 5`.
- Третья неверная попытка возвращает `attempts_exhausted`: код больше
  не принимается, нужен новый.
- Порядок при успешном входе:
  1. заказы и заявки, у которых цифры телефона в контактах совпадают с номером
     и `userId` пустой, получают `userId` вошедшего;
  2. избранное гостя переходит в кабинет (объединение без повторов), гостевое
     очищается;
  3. `mergeGuestCart(userId)` из `cart/storage.js`;
  4. запись `gg-session`;
  5. событие `account:change`.
- Выход: удаляется `gg-session`, затем `account:change`.
- Список, заказ и заявка находятся по `userId`. После смены номера заказы
  остаются в кабинете.
- `reorder` кладёт позиции через `add()` из `cart/store.js`. Если позиция
  нашлась в каталоге по слагу, цена, наличие и кадр берутся из каталога,
  иначе из снимка. Позиция со слагом, которого в каталоге нет, считается снятой
  с продажи и попадает в `skipped`.
- `saveAddress`: одиннадцатый адрес — `limit`; адрес с той же улицей и квартирой
  уже есть — `duplicate`, он не сохраняется второй раз.
- `deleteAccount` удаляет запись пользователя, адреса, избранное и его корзину.
  Заказы и заявки остаются.

#### Хранилища

**`cart/storage.js`.** Новые экспорты: `listOrders()`, `listRequests()`,
`updateOrder(number, patch)`, `updateRequest(number, patch)`,
`mergeGuestCart(userId)`, `removeUserCart(userId)`.

- Ключ корзины — `gg-cart` у гостя и `gg-cart:<userId>` у вошедшего.
  Текущий ключ определяется при каждом чтении через `session.js`.
- Если localStorage недоступен, записи живут в памяти модуля по тем же ключам.
  Так вход в приватном режиме не теряет гостевую корзину.
- `mergeGuestCart(userId)`: прочитать обе корзины, объединить по `id` с большим
  количеством (не больше `MAX_QTY`), записать в ключ пользователя, удалить
  гостевой ключ.
- `onExternalCartChange` слушает текущий ключ. В `store.js` обработчик внешнего
  изменения только обновляет состояние и рассылает `cart:change`, обратно
  в хранилище не пишет: иначе при входе в соседней вкладке корзина кабинета
  может записаться в чужой ключ.
- `store.js` перечитывает состояние по `account:change`.
- Шапку файла дополни абзацем «Корзина по пользователю (17.09.2026)». Строку
  README о «единственном файле, который трогает localStorage» замени на два
  файла.

**`account/storage.js`.** Ключи `gg-session` (`{ userId }`), `gg-users`
(`{ version: 1, byId, byPhone }`; в записи пользователя — профиль, адреса
и избранное), `gg-favorites` (избранное гостя). Всё в try/catch; без
localStorage — память модуля.

**`session.js`.** `currentUser()` — синхронно: в прототипе из `gg-session`
и `gg-users`, на Битриксе — из серверной разметки. `onChange(fn)`, событие
`account:change` с `{ user }`. Вход или выход в соседней вкладке тоже рассылает
событие.

**`favorites/store.js`.** `list()`, `has(id)`, `toggle(product)` → новое
состояние, `remove(id)`, `restore(snapshot, index)`, `count()`, `subscribe(fn)`.
Хранит состояние в памяти, сохраняет через `api.js`.

- Позиция — снимок, как в корзине: `id`, `slug`, `name`, `note`, `href`,
  `image`, `price`, `inStock`, `categorySlug`, `fulfillment`, `addedAt`.
  Вид считает `kindOf` при чтении.
- Если позиция нашлась в каталоге по слагу, цена, наличие и кадр берутся
  из каталога. Позиция со слагом, которого в каталоге нет, при чтении
  выбрасывается, и стор сообщает, сколько таких было.
- Не больше 200 позиций; при переполнении уходят самые старые.
- Изменения рассылаются событием `favorites:change` на `document`; соседние
  вкладки узнают через событие `storage`. По `account:change` стор
  перечитывает избранное.

### Б.4. Вход `/account/login`

Три шага на одной странице, адрес не меняется. Смена шага анимируется так же,
как смена режима на оформлении; при `prefers-reduced-motion` — без анимации.
После смены шага фокус на первом поле. Пока запрос к `api.js` не вернулся,
кнопка шага выключена, а автоотправка кода не срабатывает второй раз.

**Раскладка.** От 1024px форма стоит в колонках 1–5, вертикально по центру,
ширина формы не больше 420px. В колонках 7–12 кадр
`/media/brand/boutique-detail-01.jpg` через `createImage`, `--radius-card`,
по высоте колонки формы и не ниже 560px. Уже 1024px — только форма, отступы
как у оформления.

**Шаг 1. Телефон**

```

  в `account-copy.js`: `⚠ ПОДТВЕРДИТЬ У ЮРИСТА: текст согласия`.
- Пришли со страницы «Заказ принят» (`?from=order&n=` или `?from=request&r=`) —
  номер подставлен из этого заказа или заявки, если они есть в этом браузере.
- `rate_limit`: «Слишком много попыток. Попробуйте через {m} мин.»

**Шаг 2. Код**

```
Введите код
Отправили СМС на +7 900 123-45-67    Изменить номер

[ _ ][ _ ][ _ ][ _ ][ _ ][ _ ]

[                Войти                 ]

Новый код можно запросить через 0:59
Прототип: СМС не отправляется, код 123456
```

- `code-input.js`: одно настоящее `<input>` с `autocomplete="one-time-code"`,
  `inputmode="numeric"`, `maxlength` по длине кода и подписью «Код из СМС» для
  скринридера. Шесть ячеек рисуются под полем с `aria-hidden`, поэтому вставка
  из буфера и подстановка кода системой работают. Ячейки — 1px `--hairline`,

- «Изменить номер» — кнопка-ссылка, возвращает на шаг 1 с введённым номером.
- Таймер «Новый код можно запросить через {m:ss}». По истечении — кнопка-ссылка

  снова можно запросить; секунды не объявляются. `rate_limit` при повторной
  отправке показывается на месте этой ссылки.
- Ошибки под полем в `aria-live="assertive"`:
  - `wrong_code` — «Код не подошёл. Осталось попыток: {n}»; поле очищается,
    фокус остаётся в нём;

    выключено, пока не запрошен новый код;
  - `expired` — «Код устарел — запросите новый»; поле выключено так же.
- Строка прототипа — 0.8rem, `--fg-mute`.

с `back=/checkout`. Корзина при входе сохраняется по правилу Б.1.6.

**Оформление, вошедший.**

- Имя, телефон и почта подставлены из кабинета и остаются редактируемыми.
- Подводка режима «только заказ»: «Контакты и адрес подставили из кабинета.»,
  если адрес подставлен, иначе «Контакты подставили из кабинета.». Подводки
  двух других режимов не меняются.
- Шаг «Как получить», доставка. Есть сохранённые адреса — карточки-радиокнопки
  на основе `.cap`: название или улица первой строкой, остальное второй;
  выбран основной. Последняя карточка — «Другой адрес», она открывает нынешние
  поля. Нет сохранённых адресов — нынешние поля.
- Под полями нового адреса чекбокс «Сохранить адрес в кабинете», по умолчанию
  отмечен. В кабинете уже 10 адресов — вместо чекбокса строка «В кабинете уже
  10 адресов, этот не сохраним». Повтор сохранённого адреса молча
  не сохраняется второй раз.
- В `payload` уходят `contact.userId` и `order.addressId` либо новый адрес.
  Отмеченный новый адрес сохраняет `submitCheckout` через `saveAddress`.
- Заказ и заявка вошедшего сохраняются с `userId`.
- Смена входа в другой вкладке — по таблице в Б.3.

**«Заказ принят».**

- Вошедший: кнопка «Мои заказы» ведёт на `/account/order?n={n}`, при одной
  заявке — на `/account/request?r={r}`.
- Гость: под шагами блок «Следите за заказом в кабинете» / «Войдите по номеру
  {телефон из заказа} — заказ появится в разделе «Заказы и заявки».» / кнопка
  «Войти» на `/account/login?from=order&n={n}&back=<закодированный
  /account/order?n={n}>`. Для одной заявки — «Следите за заявкой в кабинете»
  и «заявка появится в разделе «Заказы и заявки».» с параметрами заявки.
  Заказа нет в этом браузере — текст «Войдите по номеру, который указали
  в заказе, — заказ появится в разделе «Заказы и заявки».» Кнопки «Мои заказы»
  у гостя нет.
- Комментарий у `actions.account` в `checkout-copy.js` перепиши под новое
  поведение.

### Б.9. Демонстрация

`src/js/account/demo.js`. В сборку Битрикса не попадает, в шапке файла сказано,
что это инструмент показа. Параметр работает на любой странице кабинета
и на `/favorites` и убирается из адреса через `history.replaceState`.

- `?demo=account` — вход демонстрационным пользователем «Анна»,
  +7 900 000-00-00; в фикстуре написано, что данные вымышленные.
  - Запись пользователя пересоздаётся. Его прежние заказы и заявки удаляются
    из `gg-orders` и `gg-requests` и кладутся заново. Номера демонстрационных
    заказов — от 90001, заявок — от 9001, чтобы не пересекаться со счётчиками
    прототипа (10241 и 501). Чужие записи не трогаются. Гостевая корзина при
    демонстрационном входе не сливается и не меняется.
  - Даты считаются от сегодняшнего дня:
    - заказ с двумя отгрузками: наличие «В пути» сегодня, под заказ «Ждём
      поставку» к дню готовности; вместе с ним заявка «В работе»;
    - заказ самовывозом «Готов к выдаче»;
    - два заказа «Получен», один из них прошлого месяца;
    - заказ «Отменён»;
    - заявка «Закрыта»;
    - заказ другого демонстрационного пользователя (+7 900 000-00-02, номер
      90099) — для проверки «Заказ не найден».
  - Два адреса: «Дом» (основной) и «Работа», улицы заведомо вымышленные
    («Примерная улица, 1»).
  - Избранное: три позиции в наличии, две рыбы под заказ, чёрная икра без цены
    (через менеджера) и одна позиция с несуществующим слагом — чтобы показать
    строку «больше не продаются».
- `?demo=new` на `/account/login` — запись +7 900 000-00-01 удаляется, если
  была, и открывается шаг 3 для этого номера.
- `?demo=guest` — выход.

Позиции заказов и избранного — настоящие из `catalog-products.js`, со снимками.
