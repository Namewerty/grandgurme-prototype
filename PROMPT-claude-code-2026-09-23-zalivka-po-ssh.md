## 1. Что меняется в порядке работы

Сейчас (`CLAUDE.md`, раздел «Стенд заливается только архивом из коммита»):
`npm run stand` собирает архив, архив вручную прикладывается к командной
PHP-строке в админке, `bitrix/install/stand-deploy.php` его раскладывает.

Становится: `npm run stand:deploy` из чистого коммита сам сверяет стенд,
делает копию, заливает изменившиеся файлы по SSH, обновляет манифест и чистит
кеш. Архив и `stand-deploy.php` остаются на случай, когда SSH недоступен
(и для боевого сайта, где доступа пока нет) — их не удаляй и из документации
не выбрасывай.

Список файлов, которые уезжают на стенд, прежний: его считает существующая
сборка `npm run stand` (`scripts/stand-pack.mjs`, `stand-manifest.json`).
Ничего, кроме этих путей, скрипт на сервере не трогает: `--delete` запрещён,
чужие файлы на стенде не удаляются никогда.

## 2. Скрипт `scripts/stand-ssh.mjs`

Один файл, четыре команды, подключены в `package.json`:

| Команда | Что делает |
|---|---|
| `npm run stand:drift` | сверяет стенд с последним манифестом, печатает изменённые и удалённые файлы |
| `npm run stand:deploy` | сухой прогон: печатает, что изменится, и останавливается |
| `npm run stand:deploy -- --yes` | то же плюс копия, заливка, манифест, кеш, проверка |
| `npm run stand:pull -- <путь>` | забирает файл со стенда в репозиторий по его пути от корня сайта |

### Общие правила

- Незакоммиченные изменения в отслеживаемых файлах — стоп, как у `npm run stand`.
- Сборка идёт из текущего коммита: `npm run bitrix` и упаковка, как сейчас.
  Заливается содержимое сборки, а не рабочая копия.
- Все обращения к серверу — через одно соединение с `ControlMaster`
  (`ssh -o ControlMaster=auto -o ControlPath=... -o ControlPersist=60`),
  иначе на каждом шаге будет новый вход.
- Любая команда печатает в конце одну строку итога: коммит, число изменённых
  файлов, путь к копии.

### `stand:drift`

Читает `/local/gg-stand/manifest.json` со стенда, считает `md5sum` перечисленных
в нём файлов одной командой на сервере (пути передавай через `xargs -0`,
батчами, чтобы не упереться в длину строки), сравнивает с манифестом. Печатает
`ИЗМЕНЁН` / `УДАЛЁН` по каждому расхождению и общее число. Сравнение идёт по
тем же правилам, что в `bitrix/install/stand-deploy.php` (там перевод строк
приводится к `\n` — повтори это же, иначе файлы, поправленные через админку,
дадут ложное расхождение).

### `stand:deploy`

Порядок:

1. Сборка из коммита, как сейчас.
2. `stand:drift`. Есть расхождения — стоп со списком. Продолжать только с
   `--force`, и тогда в отчёте перечислить, что будет перезаписано.
3. Сухой прогон `rsync --dry-run --itemize-changes` по списку файлов сборки.
   Вывод — это и есть «что изменится». Без `--yes` на этом и останавливаемся.
4. Копия того, что будет перезаписано: на сервере
   `/var/www/bitrix.1grandgourmet.ru/gg-stand-archive/backup-<дата>-<коммит>/`,
   с сохранением путей (`tar` по списку изменяющихся файлов, существующих на
   стенде). Копия делается до заливки и печатается в отчёте.
5. Заливка:
   `rsync -a --checksum --itemize-changes --chmod=Dg+ws,Fg+w --files-from=<список> <сборка>/ gg-stand:/var/www/bitrix.1grandgourmet.ru/www/`.
   Без `--delete`, без `--owner`, без `--group`: владельца меняем не мы.
6. Манифест: собранный `stand-manifest.json` кладётся в
   `/local/gg-stand/manifest.json` (тот же формат, что пишет `stand-deploy.php`,
   с полями `commit`, `branch`, `builtAt`, `files`) — на него опирается
   `stand:drift` и записки Cowork.
7. Кеш Битрикса: `rm -rf bitrix/cache/* bitrix/managed_cache/* bitrix/stack_cache/*`
   внутри корня сайта. Ничего, кроме этих трёх папок, не чистим.
8. Проверка после заливки: запросить с сервера
   `curl -s -o /dev/null -w "%{http_code}"` по адресам `/`, `/catalog/`,
   `/catalog/ryba/`, `/cart/`, `/account/login/` и убедиться, что везде 200.
   Плюс сверить `/local/gg-stand/manifest.json` — коммит должен совпасть с тем,
   что заливали. Ошибка — печатаем и предлагаем откат.
9. Тег `stand-<дата>` на коммит и `git push --tags`.

### Откат

Отдельной команды не заводим: копия лежит распакуемым архивом, и откат — одна
строка `tar -xf <копия> -C <корень сайта>`, которую скрипт печатает в конце
каждой заливки. Эту строку обязательно выводи: ею пользуется человек, а не скрипт.

### `stand:pull`

Забирает файл со стенда (`scp`/`rsync` в обратную сторону) в рабочую копию по
тому же пути, куда его кладёт сборка (`bitrix/templates/grandgurme/...`,
`deploy-src/...`, `bitrix/server/...` — правило из `CLAUDE.md`, раздел «Правки
прямо на стенде»). Нужен, когда на стенде что-то поправили руками и это надо
вернуть в репозиторий.

## 3. Чего скрипт не делает

- Не трогает обмен с 1С, `bitrix/modules`, ядро и `upload`.
- Не удаляет на сервере ничего, кроме содержимого трёх папок кеша.
- Не заливает из грязного дерева и не заливает ветку, отличную от `main`,
  без явного `--force`.
- Не кладёт архивы и патчи внутрь корня сайта: копии уходят в
  `gg-stand-archive`, которая лежит выше корня (nginx её не отдаёт).

## 4. Проверка задания

1. `npm run stand:drift` на текущем `main` — расхождений быть не должно
   (на стенде коммит `6e892f7`).
2. `npm run stand:deploy` без `--yes` — печатает «изменится 0 файлов».
3. `npm run stand:deploy -- --yes` на том же коммите — заливка вхолостую:
   файлы не меняются, манифест переписывается, кеш чистится, все адреса
   отдают 200. Это и есть настоящая проверка механизма.
4. Поправь на стенде один файл руками (`ssh gg-stand "..."`, например
   добавь пробел в конец `local/gg-stand/manifest.json`-независимого файла
   вроде `deploy-src`-страницы) — `stand:drift` должен это показать,
   `stand:deploy` — остановиться. Верни файл `stand:pull`-ом или залей заново
   с `--force` и убедись, что в копии лежит прежняя версия.
5. `npm run stand` (старый путь с архивом) по-прежнему собирается.
