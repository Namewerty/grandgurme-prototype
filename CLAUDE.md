# Как вести работу над сайтом «№1 Гранд Гурмэ»

Этот файл читает любой агент, который трогает сайт: Claude Code в папке,
Cowork, Claude in Chrome в админке Битрикса. Правила короткие, и они
обязательны: весь хаос до 17.09.2026 появился из-за того, что одна и та же
правка жила в трёх местах по-разному.

## Одно место правды

Правда — ветка `main` на GitHub (`Namewerty/grandgurme-prototype`).
Всё остальное — копии, сделанные из коммита:

- папка «Сайт» в OneDrive — рабочая копия репозитория;
- прототип на Vercel — `npm run build` из коммита, тег `vercel-<дата>`;
- стенд `bitrix.grandgurme.ru` — `npm run stand:deploy` из коммита по SSH, тег `stand-<дата>`.

Прототип и Битрикс — не две версии сайта, а две сборки одних исходников
(`src/`, `bitrix/`, `deploy-src/`). Правка карточки, корзины или
оформления делается один раз в исходниках и уезжает в обе сборки.

## Любая правка заканчивается коммитом в `main`

**Claude Code** (есть git и доступ к GitHub): в начале сессии `git pull`
и применить патчи из `_patches/` (ниже); в конце — коммит и `git push`.

**Cowork и Claude in Chrome** (пушить в GitHub не могут): клонируют
репозиторий у себя, коммитят и кладут результат в папку `_patches/` в корне
папки «Сайт». Лучше всего — git bundle: он сохраняет хеши коммитов, и коммит,
записанный в манифест стенда, совпадёт с тем, что окажется на GitHub:

```
git bundle create _patches/<дата>-<тема>.bundle origin/main..HEAD
```

Запасной вариант — патчи (`git format-patch origin/main..HEAD -o _patches/`),
хеши при этом поменяются. Если git в окружении нет — архив изменённых файлов
с путями от корня репозитория и `_patches/<дата>-<тема>.md`: что и зачем.

**Первое действие Claude Code в новой сессии**, если `_patches/` не пустая:

```
git pull
git fetch _patches/<файл>.bundle HEAD && git merge --ff-only FETCH_HEAD   # для .bundle
git am --3way _patches/*.patch                                             # для .patch
git push --follow-tags
```

затем перенести применённые файлы в `_patches/applied/`. Если `--ff-only`
не проходит (в `main` за это время появились коммиты) или `git am` даёт
конфликт — остановиться и показать Денису, не решать молча.

## Стенд заливается по SSH из коммита

С 23.09.2026 основной путь — прямая заливка по SSH одной командой:

```
npm run stand:drift              # что на стенде правили мимо репозитория
npm run stand:deploy             # сухой прогон: что изменится, и стоп
npm run stand:deploy -- --yes    # копия, заливка, манифест, кеш, проверка
npm run stand:pull -- <путь>     # забрать файл со стенда в репозиторий
```

Доступ в репозиторий не попадает: скрипт знает только имя хоста `gg-stand`,
а адрес, логин и ключ лежат в `~/.ssh/config` на машине. Переопределяется
переменной окружения `GG_STAND_SSH`. Корень сайта на сервере — константа
в `scripts/stand-ssh.mjs`.

Что делает `stand:deploy -- --yes`, по порядку:

1. Не заливает из грязного дерева и не заливает ветку, кроме `main`, без `--force`.
2. Собирает из текущего коммита (`npm run bitrix`) — уезжает сборка, а не рабочая копия.
3. Сверяет стенд с последним манифестом. Есть правки мимо репозитория — стоп
   со списком; продолжить можно только `--force`, и тогда список перезаписываемого
   печатается отдельно.
4. Кладёт копию всего, что будет перезаписано, в `backup-<дата>-<коммит>.tar.gz`
   рядом с корнем сайта — **до** заливки.
5. Заливает `rsync`-ом только изменившиеся файлы. Без `--delete`: чужие файлы
   на стенде не удаляются никогда.
6. Пишет манифест в `/local/gg-stand/manifest.json` и чистит три папки кеша
   Битрикса (`bitrix/cache`, `bitrix/managed_cache`, `bitrix/stack_cache`).
   Больше на сервере не удаляется ничего. Дочистить их `deploy` не может —
   папки созданы php-fpm без групповой записи, — поэтому заливка кладёт метку
   `/local/gg-stand/cache-flush`, и первый же хит сайта чистит кеш сам
   (обработчик в `bitrix/server/local/php_interface/init.php`). **Правку
   настройки, сделанную скриптом по SSH, без этого сайт не увидит:
   23.09.2026 на этом потерялись полдня.**
7. Проверяет: `/`, `/catalog/`, `/catalog/ryba/`, `/cart/`, `/account/login/`
   отдают 200, коммит в манифесте совпал, суммы всех файлов сошлись.
8. Ставит тег `stand-<дата>` и пушит его.

**Скрипты установки — тоже по SSH.** Заливка кладёт файлы, но ничего
не устанавливает. Инфоблоки, почтовые события, агенты и опции ставит
`bitrix/install/*.php`, и запускаются они так:

```
npm run stand:php -- bitrix/install/gg-catalog-sections-install.php                  # режим из файла, обычно check
npm run stand:php -- bitrix/install/gg-catalog-sections-install.php --mode=install   # выполнить
npm run stand:php -- <одноразовый скрипт> --dirty                                    # взять из рабочей копии
```

Скрипт берётся из текущего коммита (`--dirty` — из рабочей копии, для
одноразовых проверок; такие файлы не коммитим). `--mode=` подменяет в теле
строку `$mode = '...';`. На сервере скрипт живёт во временном файле вне корня
сайта и удаляется после запуска. Всё, кроме `check`, ставит метку сброса кеша
и дёргает сайт, чтобы правку было видно сразу.

Командная PHP-строка в админке остаётся запасным путём — она работает
от `www-data` и годится там, где SSH нет (боевой сайт).

⚠ **Инфоблок и записи в нём ставятся за два прогона.** Создать инфоблок
и тут же добавить в него элемент в одном хите не выходит: `CIBlockElement::Add`
отвечает «Неверный код информационного блока» — Битрикс ещё держит в кеше
список инфоблоков без нового, а почистить его `deploy` не может (см. пункт 6).
Скрипты идемпотентные, поэтому лечится повторным запуском: первый создаёт
инфоблок, второй — записи. Проверяйте вывод, а не код возврата.

**Страницы, которые правятся в админке.** Руководство меняет тексты сайта
визуальным редактором, без разработчика. Такие страницы перечислены в
`scripts/stand-files.mjs` (`ADMIN_EDITED`; сейчас там одна — `/storage/index.php`)
и живут по своему правилу:

- файла на стенде нет — заливка его ставит;
- файл есть — заливка не трогает его никогда, даже с `--force`;
- `npm run stand:drift` пишет о нём отдельной строкой «правится в админке»,
  а не считает расхождением.

Вернуть такую страницу к виду из репозитория можно только одним способом:
удалить её на стенде и залить заново. Это осознанное действие человека,
а не побочный эффект заливки. Страница в репозитории собирается обычной
разметкой — без массивов, циклов и include шаблона: иначе визуальный
редактор Битрикса её содержимого не покажет.

**Откат.** Отдельной команды нет: копия — распакуемый архив, и скрипт в конце
каждой заливки печатает готовую строку вида
`ssh gg-stand "tar -xzf <копия> -C /var/www/bitrix.1grandgourmet.ru/www"`.
Ею пользуется человек, а не скрипт.

**Список файлов** у обоих путей заливки один — `scripts/stand-files.mjs`.
Ничего сверх него скрипт на сервере не трогает.

## Запасной путь: архив через админку

Остаётся на случай, когда SSH не отвечает, и для боевого сайта, где доступа
пока нет. Удалять его и выбрасывать из документации нельзя.

1. `npm run stand` — сборка и архив `grandgurme-stand-<дата>-<коммит>.zip`.
   С незакоммиченными правками архив не собирается.
2. В админке: «Настройки → Инструменты → Командная PHP-строка», вставить
   `bitrix/install/stand-deploy.php` с `$mode = 'check'`, приложив архив
   (или положив его в `/upload/gg-stand/`). Скрипт покажет, что обновится,
   и остановится, если файлы на стенде правили руками.
3. Если чисто — тот же скрипт с `$mode = 'deploy'`. После заливки архив
   переносится из `/upload/gg-stand/` в `/var/www/bitrix.1grandgourmet.ru/gg-stand-archive/`,
   на уровень выше корня сайта: `/upload/` nginx отдаёт любому без входа.
4. `git tag stand-<дата> <коммит> && git push --tags`.

Манифест у обоих путей один и тот же, в одном месте
(`/local/gg-stand/manifest.json`): после заливки архивом `npm run stand:drift`
продолжает работать, и наоборот. Таблицы md5 в промптах руками не пишутся.

## Правки прямо на стенде

Бывает, что править нужно на Битриксе: выгрузка из 1С, поиск, `init.php`,
`urlrewrite.php`. Это нормально, но правка сразу возвращается в репозиторий:

- файлы шаблона и страниц — в свои пути в `bitrix/templates/grandgurme/`
  и `deploy-src/`;
- файлы ядра сайта — в `bitrix/server/` с путём от корня сайта
  (`bitrix/server/local/php_interface/init.php`, `bitrix/server/urlrewrite.php`).

Проверка, что на стенде нет забытых правок: `npm run stand:drift` (или
`stand-deploy.php` с `$mode = 'drift'`, если SSH не отвечает). Непустой список —
сначала в репозиторий, потом заливка. Забрать файл со стенда в его путь
в репозитории: `npm run stand:pull -- /catalog/index.php`.

Настройки админки, которые не файлы (инфоблоки, почтовые шаблоны, службы
доставки, свойства заказа, опции модулей), записываются строкой в
`bitrix/STAND-SETTINGS.md`: дата, что, где, зачем. Если настройку придётся
повторить на боевом сайте — скриптом в `bitrix/install/`.

## Нельзя

- Не трогать обмен с 1С, выгрузку, типы цен — сайт подстраивается под выгрузку.
- Не класть копии `.bak`, архивы и патчи в папки сайта на сервере: nginx отдаёт
  их наружу вместе с исходниками PHP.
- Не оформлять заказы на стенде: они уйдут в обмен с 1С. Проверка заказа —
  сухой прогон без `save()`.
- Не заливать на стенд сборку не из `main` и не из коммита.
- Не заливать с `--force`, не разобравшись, что именно затирается: `--force`
  перезаписывает правки, сделанные на стенде мимо репозитория.
- Не заливать руками через `rsync`, `scp` или файловый менеджер в обход
  `npm run stand:deploy`: манифест не обновится, и следующая сверка соврёт.
- Не переписывать страницы из списка `ADMIN_EDITED` в обход правила выше:
  на стенде в них правка контент-менеджера, и она никуда не сохранена.
- Не открывать на стенде заведомо несуществующие адреса: «Контроль активности»
  банит IP за серию 404.

## Где что описано

- `README.md` — прототип целиком, «Корзина и оформление», «Что осталось до полного запуска».
- `bitrix/templates/grandgurme/README.md` — шаблон Битрикса и что выяснилось на стенде.
- `bitrix/STAND-SETTINGS.md` — настройки стенда, сделанные руками в админке.
- `bitrix/install/` — скрипты для командной PHP-строки.
- `scripts/stand-ssh.mjs` — заливка по SSH; `scripts/stand-files.mjs` — список файлов,
  которые уезжают на стенд, один на оба пути заливки, и список страниц,
  которые правятся в админке.
- `RAZVEDKA-korobok.md` — что о коробках уже есть в выгрузке 1С и вопросы
  к тому, кто её ведёт.
- `PERENOS-*.md` — записки о переносе прототипа на стенд.
